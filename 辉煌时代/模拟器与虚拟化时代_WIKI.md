## 1. 时代概览

「模拟器」这个词的字面意思很朴素：用一台机器的资源，重现另一台机器的行为。1990 年代中后期，PC 的运算能力第一次足够宽裕，可以在软件里完整地装下一台红白机。玩家按下电源，屏幕上出现的是另一台机器的启动画面，而屏幕上发生的一切，实际都由宿主机的中央处理器（Central Processing Unit，CPU）逐条算出来。

这件事的后续远比怀旧更长。为了让 PC 跑动 NES（Nintendo Entertainment System，日版称 Family Computer，中文语境多叫红白机或小霸王），工程师被迫去理解一颗图像处理单元（Picture Processing Unit，PPU）在哪一拍读哪一张图块、卡带上的分页芯片如何切换存储体、一帧画面由多少条扫描线组成。为了让 PC 跑动 Nintendo 64 和 PlayStation，他们又被逼到三维图形流水线、光盘子通道、几何协处理器面前。再往后，为了让 PC 跑动 PlayStation 3，他们不得不正面处理一颗异构的 Cell 处理器；为了在 PC 上顺畅运行原来只写给 Windows 和 Direct3D 的游戏，他们转去写兼容层与图形翻译层；为了在一台物理服务器上同时跑许多台虚拟服务器，他们把「重现一台机器」的手艺搬进了操作系统内核与处理器硬件。

本文覆盖的这条线索，可以概括成一句话：现代电脑逐步学会把别人的 CPU、显卡、总线、外设、系统服务乃至整台机器重新抽象并复现在自己体内。它先让人在 PC 上玩到 NES，后来又逼工程师去面对 PS3 的异构 Cell、现代 GPU 的图形翻译与 hypervisor 时代的整机虚拟化，最终把「怀旧工具」一路做成了数字保存、底层工程与现代计算基础设施的一部分。

需要先把几个常被混用的词分清。**模拟（emulation）**指用软件或可编程逻辑逐条重现目标机器指令与硬件行为，代表是家用机模拟器；**虚拟化（virtualization）**指让多份指令流直接跑在同一套处理器上，由硬件与一层薄薄的虚拟机监控器（hypervisor）负责隔离，代表是服务器虚拟化；**兼容层（compatibility layer）**指不模拟指令，只把目标平台的应用程序接口（Application Programming Interface，API）翻译成宿主平台的调用，代表是 Wine；**图形翻译层**指把一种图形 API 的调用改写成另一种，代表是 DXVK。这四条路线在 1990 年代到 2010 年代交错发展，后来又在同一批工程师、同一批项目里汇合。

本篇的核心张力，落在「历史地位」与「市场结果」的错位上。模拟器写下了若干里程碑式的司法判例，也养活了从街机厅到掌机的整段记忆，却几乎从不是赚钱的生意：做出首个可玩 Nintendo 64 模拟器的两位作者在任天堂的诉讼威胁下消失；打赢 Sony 的 Connectix 最终把产品卖给了 Sony；打赢官司的 Bleem 被诉讼拖到停业。与此同时，被它们「偷跑」的技术，后来又以官方模拟器、向后兼容、虚拟机与兼容层的形式回到市场上，成为厂商与云服务商的标准配置。留下最多、赢得最少，是这一行反复出现的形状。

按「为什么重要 / 留下什么 / 如何影响后来 / 玩家当时怎样体验」这四问去看，模拟器的答案也并不单薄：它在技术上第一次把「机器」变成了可以阅读、比较、修改与保存的对象；它留下了一批至今仍在维护的开源项目与判例；它影响了后来的虚拟化、兼容层、可复现测试与数字保存；而玩家当时的体验，往往是在自购或借来的 PC 上，第一次见到租不到、买不起、也没在本地上架的游戏。

需要与今天的语汇划清边界。用「云」「容器」「零信任」去解释 1990 年代的模拟器浪潮，是把后来的需求倒灌回过去。当年的真实问题很具体：厂商停产、卡带损坏、街机基板老化、PC 上买不到某些游戏、开发者在 Linux 上要跑 Windows 工具。后面这些概念是 2010 年代才长出来的，它们借用了当年打下的技术底子，却不是当年的出发点。

## 2. 时代时间线

### 2.1 1990 年代前中期：8 位机与街机走进 PC

这一阶段的主线是「PC 运算能力首次够用」。486 与初代 Pentium 机器上，模拟一台 8 位游戏机已经是可行任务；模拟器在 DOS 下以极窄的代码体积出现，通过软盘与公告板系统（Bulletin Board System，BBS）传播，ROM 文件则在 FTP 站点与后来的专题网站之间流转。街机侧，意大利学生 Nicola Salmoria 从复现《吃豆人》的一个小程序起步，两年内把它扩成能跑数百款街机游戏的 Multiple Arcade Machine Emulator（MAME），并把它当成一份可以持续维护的硬件档案。家用机侧，超任模拟器领域出现了两条早期的源代码线，Gary Henderson 与 Jeremy Koot 的成果后来合并成了 Snes9x；同期的 Mystic 是能在 DOS 上跑得很快的 NES 模拟器，Genecyst 则在做世嘉 MD（Mega Drive / Genesis）。这一时期的作品多以「能跑起来」为目标，帧率与兼容性都还在原始阶段。

### 2.2 1997–2000：并行推进与法律的正面冲撞

1999 年 1 月，两位化名 RealityMan 与 Epsilon 的开发者发布了 UltraHLE，这是第一个能在当时的 PC 上以可玩帧率运行 Nintendo 64 商业游戏的模拟器。它走的是一条新路：不去逐条精确模拟硬件，而是截住游戏对主机库函数的调用并直接重新实现。任天堂随即着手起诉，两位作者在压力下退场。同一时期，Connectix 在 1999 年 1 月的 MacWorld 上公布了 Virtual Game Station，让 Mac 能玩 PlayStation 光盘；Sony 于 1 月 27 日起诉，并一度拿到临时禁令；2000 年 2 月，美国联邦第九巡回上诉法院推翻了这一禁令，认定 Connectix 为逆向工程而复制 BIOS 属于合理使用。以三人团队起步的 Bleem 则在 1999 年推出 Windows 版 PlayStation 模拟器，Sony 对它的两次临时限制申请都未获准。行业组织 IDSA 也在 1999 年向网络服务商发信，要求撤下街机 ROM 文件。MAME 没有因此停下。

### 2.3 2000–2010：插件化、精确度追求与虚拟化成型

这一阶段出现了两条看似相反、实则互补的路线。一条是「把模块拆开」：以 ePSXe 为代表的 PlayStation 模拟器把图形、音频、光驱、输入各自做成可替换的插件，让同一套核心能适配差异极大的 PC 硬件。另一条是「把精度做到底」：bsnes（后更名 higan）等超任模拟器开始追求逐周期、逐扫描线的准确，宁可慢也要让那些依赖精确时序的卡带正常工作。系统侧，Fabrice Bellard 于 2003 年发布 QEMU，把动态翻译用于整机与用户态两个层次；Xen 同年从剑桥大学的研究项目成形；KVM 在 2006 年由 Avi Kivity 于 Qumranet 启动，并于次年被并入 Linux 内核，把虚拟化下沉到系统内核。微软则在 2008 年随 Windows Server 推出 Hyper-V。Wine 在这一阶段持续长大，终于 2008 年发布 1.0 稳定版。

### 2.4 2010–2020：掌机、手机、GPU 翻译与兼容层

主机硬件进入多核与异构时代后，模拟器的重心从「模拟一颗 CPU」变成「同时模拟一颗主 CPU、若干协处理器和一块当代 GPU」。RPCS3 于 2011 年成立，用多年时间把 Cell 的 PPU 与 SPU、以及 NVIDIA RSX 图形核心一块块攻下。掌机侧，PPSSPP（2012）与 Citra（2013）分别面向 PSP 与 Nintendo 3DS；安卓平台上则出现了把 ARM 应用搬到 x86 手机的运行方案。街机侧，MAME 与 MESS 在 2015 年合并，把家用机的驱动也纳入同一套框架。2018 年，Valve 发布基于 Wine 的 Proton 与 Direct3D 到 Vulkan 的翻译层 DXVK，让 Windows 游戏在 Linux 上的可玩性大幅提升；2020 年，面向 Direct3D 12 的 vkd3d-proton 从上游分叉出来。

### 2.5 2020 至今：兼容层成为基础设施、法律口径收紧

2021 年 Steam Deck 发布，兼容层第一次成为一款量产消费设备的默认运行方式。RPCS3 在 2021 至 2022 年间把支持扩到 ARM64，并暴露了 16KB 内存页带来的新问题。厂商一侧，官方模拟与向后兼容成为常态：任天堂的迷你复刻机、Switch Online 的经典游戏库、PlayStation Plus 的经典目录、Xbox 的向后兼容，都在用不同技术路线重卖旧作。法律一侧则明显收紧：2024 年，任天堂与 Switch 模拟器 Yuzu 的开发者达成和解并致其停运，另一款 Switch 模拟器 Ryujinx 随后也停止开发。这条线索至今仍在推进，本文对 2020 年以后的部分按观察口径处理。

## 4. 模拟的基本原理（以 NES 为讲法）

### 4.1 一颗 CPU 的取指、译码与执行

模拟器要做的事，可以拆成一句朴素的描述：在宿主机的内存里保存目标机器的全部可见状态，再按目标机器硬件的时间表，一个周期一个周期地推进这个状态。以 NES 为例，目标机器的可见状态包括 CPU 的寄存器组、内存、以及图像与声音芯片的内部计数器。

NES 的主 CPU 是理光 2A03，指令集与 MOS 6502 基本一致，缺少十进制模式。模拟它，就是在内存里维护通用寄存器 A、X、Y，程序计数器 PC，栈指针 SP，状态寄存器 P，以及一块 2KB 的内部存储区。CPU 循环反复做三件事：从 PC 指向的地址取出一个字节的操作码，按操作码决定后续要读几个字节的操作数、做哪一种运算，然后更新寄存器与状态位。每条指令消耗的周期数不等，跨越页边界的取数还要多花一拍。模拟器可以选择按指令粒度推进，也可以选择按周期粒度推进；后者更准，代价是每一步都要额外判断中断与芯片之间的信号。

与时序有关的细节，决定了模拟器能跑什么。CPU 有可屏蔽中断与复位向量，声音芯片和图像芯片都能向它发中断。写到一个特定寄存器地址，就能触发一次直接存储器访问（Direct Memory Access，DMA），把 256 字节一次搬进图像芯片的对象属性存储器。模拟器如果不实现这条 DMA 路径，画面上的活动块就会错位。

### 4.2 PPU 与寄存器：把像素算在正确的那一拍上

NES 的图像处理单元是一颗独立的芯片，拥有自己的内存与时钟。它对 CPU 暴露八个寄存器，名义上位于地址 `$2000` 到 `$2007`，由于地址译码不完整，这八个寄存器在 `$2008` 到 `$3FFF` 之间每 8 字节重复一次；写到 `$3456` 与写到 `$2006` 效果相同。这八个寄存器分别是控制寄存器 `PPUCTRL`（`$2000`）、掩码寄存器 `PPUMASK`（`$2001`）、状态寄存器 `PPUSTATUS`（`$2002`）、对象属性地址 `OAMADDR`（`$2003`）、对象属性数据 `OAMDATA`（`$2004`）、滚动寄存器 `PPUSCROLL`（`$2005`）、地址寄存器 `PPUADDR`（`$2006`）与数据端口 `PPUDATA`（`$2007`）。它们内部还维护着一组不可直接读取的计数器，用来记录当前滚动位置与写地址的高低位。

图像芯片按扫描线推进画面。NTSC 制式下，一条扫描线是 341 个图像时钟，一帧是 262 条扫描线；每个图像时钟输出一个像素，而一个 CPU 时钟对应三个图像时钟。真正的画面只有 256 个像素宽、240 条扫描线高，其余的时钟与扫描线落在水平与垂直消隐区。进入第 241 条扫描线时，芯片把垂直消隐标志置位，并可以向 CPU 发出非屏蔽中断（Non-Maskable Interrupt，NMI）；多数游戏把更新画面所需的写入都放在这段垂直消隐期里完成。

这套设计带来两个后果。第一，画面不是「一次性算出整帧」，而是「在扫描线经过的那一刻，芯片手里的寄存器是什么值，那条线上的像素就长什么样」。于是程序在画面中途改动滚动寄存器，就能做出分屏：顶部一行状态栏与下方滚动世界各走各的。许多作品用「精灵 0 命中」标志来判断扫到某一行的时机，再在那一行切换滚动。第二，精度要求从「指令级」上升到「周期级」。垂直消隐标志在读取状态寄存器时会被清掉，而且在标志置位前后一拍读取还会表现出抑制行为；如果模拟器不重现这个边角行为，依赖它的游戏就会出现卡顿甚至判错。一条被反复引用的做法是：让 CPU 按约 29781 个时钟的间隔去轮询状态寄存器，借由逐帧错位，把 CPU 与图像芯片的时序对齐。

图像芯片还有一处与「越界写入」有关的特性。它内部有一条通信总线，长期寄存在容量很大的走线上，表现为一个会衰减的动态锁存器；任何一次写寄存器都会填充这个锁存器，读取本应「只写」的寄存器或状态寄存器里未使用的位，读到的是锁存器里的残留值，而其中至少一位会在 3 到 30 毫秒之间衰减。模拟器若把这个「开放总线」当成恒定的 0 或 1，画面有时也会对不上。

### 4.3 mapper：卡带里的分页机关

NES 的 CPU 地址空间留给卡带的窗口有限。为了让容量远大于窗口的卡带能被访问，卡带里往往还焊着一颗分页芯片，业界叫 mapper（映射器）。程序向卡带区写入一个值，mapper 就按这个值把某一段存储体（bank）切进 CPU 或图像芯片的地址窗口。控制寄存器、切换粒度、是否带扫描线中断计数器，各家 mapper 各不相同。早年的卡带多为「无分页」或简单分页，随着卡带容量上升，出现了能在运行中切换程序段与图块段、并附带一个可编程中断计数器的选择器，这类中断计数器常被用来精确地按扫描线分割画面。

对模拟器而言，mapper 是最无法忽略的一层。CPU 与图像芯片可以用一套通用逻辑模拟，mapper 却要为每一种型号单独写一套寄存器语义；一旦某一款 mapper 的边界行为没实现，对应卡带就会在黑屏、花屏或卡死之间随机表现。许多早期模拟器只能跑一部分游戏，原因就落在 mapper 覆盖面上。反过来，mapper 也是研究者最好的切入口之一：卡带本身在用自己的方式，告诉后人那颗主机的地址空间当初是怎么被省下来的。

### 4.4 帧、扫描线与「精确」的含义

把上面几层合起来看，一台 NES 的可见状态是 CPU 寄存器、2KB 内存、图像芯片的寄存器与内部计数器、图像芯片的独立内存、对象属性存储器、声音通道状态，以及 mapper 的当前分页。模拟器每推进一帧，就要让这些状态按各自的时钟走完 341×262 个图像时钟。所谓「周期精确」（cycle-accurate），指的正是模拟器内部也维持这样一套时钟，让任何一次读写都发生在与真机相同的相对位置上。

精度不是学术洁癖。红白机时代末期的一些作品已经在用扫描线中断、精灵 0 命中、开放总线残留值来做出超出常规的效果；同人制作与速通社区也会主动利用这些边角行为。于是一部分模拟器选择牺牲速度换取可复现的时序，用它们来跑速通验证（Tool-Assisted Speedrun，TAS）与逐帧比较，另一部分则选择在自己的机器上尽量快地让普通玩家把卡带玩完。两种取向的分岔，从红白机一直延续到后来所有世代。

另有一类变异硬件值得一提。红白机的授权克隆机在南美、东欧与东亚广泛流通，其中一些的时钟与官方机型略有偏差，会让「垂直消隐标志能否连续两帧都被漏读」这类边角行为表现不同。模拟器若只对着一种官方机型写死时序，在这些机器上就未必对得上。

### 4.5 内存地图与图块：可见与不可见的部分

把 NES 的地址空间摊开看，模拟器需要维护的其实是两张地图。CPU 侧的低地址是 2KB 内部存储，它在整个低区里反复镜像；再往上是图像芯片的八个寄存器、声音与手柄等输入输出端口、一条用于直接搬运 256 字节到图像芯片对象属性的通道，以及留给卡带的程序存储区。图像芯片侧则有自己的三块空间：图块表、名称表与调色板。把这四张表对齐，是模拟器「能出画面」的最低门槛。

图像芯片的图块表放在自己的地址 `$0000` 到 `$1FFF`，通常来自卡带上的只读存储，早期也有少量卡带使用可写存储。名称表描述屏幕上每一格用哪一块图块、以及用哪一组调色板，物理上只有 2KB 的显存，通过不同的镜像方式摊到两块名称表的位置上，于是同一块显存可能水平镜像、垂直镜像或按四屏排布，游戏利用这一点做出滚动与状态栏的取舍。调色板位于 `$3F00` 起始的 32 字节，分为一组背景色与一组精灵色，每组四色，第一格是整个画面的背景基色，相邻项之间每 32 字节重复一次。

控制寄存器决定画面的大框架：使用哪一块名称表作为基准、访问显存时地址每次增加 1 还是 32、精灵图块取自哪一张表、精灵是 8×8 还是 8×16、以及是否允许垂直消隐中断。掩码寄存器决定显示什么：是否显示背景与精灵、是否屏蔽最左侧若干列、是否做灰度或强调某个颜色通道。状态寄存器则只报告三件事——是否处于垂直消隐、精灵 0 是否与背景重叠、同一行上是否出现超过八只精灵。这三件事恰恰是程序用来对时序的工具：精灵 0 命中用来切分画面，精灵溢出用来间接判断扫描线位置。

对象属性存储器的容量是 64 只精灵，每只四个字节，记录纵坐标、图块编号、属性与横坐标。图像芯片每推进一条扫描线，都要先在这 64 只里挑出本行可见的前八只，再在扫描线前半段取它们的图块数据；这条「精灵评估」流水线决定了每行最多显示八只精灵，超出的会被丢弃并置起溢出标志。对模拟器来说，精灵评估的时机与结果都必须按扫描线推进，不能等整帧算完再统一切图，否则依赖中途改动的画面就会错位。

还有一处容易忽略的行为与数据端口有关。通过数据端口读图块表或名称表时，返回的是上一次读取留下的缓冲值，当前地址的数据要等下一次读取才出现；读取调色板则是立即返回，不经过缓冲。写入地址寄存器时，高低字节分两次送入，中间任何一次读取状态寄存器都会把这组写入的次序复位。这些细节单独看都不起眼，却构成了游戏与硬件之间那份没有写在手册里的约定。

## 5. 从 16/32 位到 3D 主机：模拟对象的扩张

### 5.1 从单芯片到多芯片同步

NES 的模拟对象基本是一颗 CPU 加一颗图像芯片加一颗声音芯片，三者职责清楚。进入 16 位世代后，模拟对象从「单核」变成「多核 + 协处理器」。超级任天堂（Super Famicom / SNES）主 CPU 是 65816 内核，音频侧另有一颗 SPC700 加一颗数字信号处理器（Digital Signal Processor，DSP），两者各有独立内存，靠一组通信端口交换数据；画面侧还支持多种图块模式与一种能对整块背景做仿射变换的模式。更麻烦的是，一些卡带里还焊着额外的运算芯片：有的做浮点运算，有的提供更高主频的协处理内核，有的把整台机器的能力再叠一层。模拟器必须同时推进这些互相等待的部件，任何一方慢一拍都会牵连全局。

世嘉 MD 的结构类似：一颗 68000 主 CPU、一颗 Z80 副 CPU、一颗调频声音芯片与一块视频显示芯片。到了土星（Sega Saturn），部件数量进一步上升：两颗 SH-2 主 CPU、一颗 68000、两块视频显示芯片、一颗几何运算 DSP 与光驱控制器。土星模拟长期被视为难题，一个重要原因是它把「多芯片协同」推到了当时硬件的极限，而这些芯片之间的同步关系在公开资料里并不完整。

### 5.2 3D 图形流水线带来的整层新状态

PlayStation 把模拟难度换了一个维度。它的 MIPS R3000 内核外面，挂着一颗几何变换引擎、一颗视频解码器、一块光栅化显示芯片与一颗声音芯片。真正让模拟器头疼的是显示芯片的三维管线：它没有深度缓冲，纹理贴图采用仿射方式，在透视下会出现明显抖动，顶点会被量化到整数坐标上。这些「缺陷」恰恰是那个时代画面的辨识度来源。模拟器若用一套标准的、正确透视的现代光栅化去替代它，画面会「太干净」，与真机不符；若想还原那种抖动，就得把定点数、抖动表与多边形排序都照着实现。

Nintendo 64 又把问题推到「可编程」这一层。它的主芯片外面是一颗现实协处理器，内含一个可编程的信号处理器与一个光栅化处理器；两部分都靠微码驱动，而不同游戏使用的微码版本不同。逐条模拟这套微码既慢又难，UltraHLE 选择绕开它，直接识别游戏发出的高层调用并用自己的绘图代码顶替，从而在当年的 Pentium II 上跑出接近可玩的帧率。这条路线把「模拟」与「重实现」的界限推到了前台。

索尼的 PlayStation 2 则是另一种情形。它的情感引擎主 CPU 外围挂着矢量运算单元，图形侧是一颗带宽极高的合成器，整机设计与前一世代不同，但公开资料相对充分，模拟器得以用多年时间逐步逼近。真正把异构难度推上顶点的是后来的 PlayStation 3，本文单列一章讨论。

### 5.3 外设与介质

主机世代更替时，被模拟的对象不止芯片。光枪依赖阴极射线管（Cathode Ray Tube，CRT）逐行扫描的物理时序，在液晶显示器上无法原样工作，模拟器只能改用鼠标坐标或屏幕坐标来代偿；手柄的震动、多手柄分插、记忆卡、键盘鼠标、光驱与调制解调器各有自己的协议与时序。光盘世代还带来介质层的问题：光驱的寻道时间、子通道数据、区域码与复制保护，都会影响程序能否启动。模拟器若把光盘当成一个无限快的文件读取，某些依赖读盘节奏触发事件的游戏就会走错分支。

把 16 位到 3D 主机这一段串起来看，难度爆炸并不来自某一颗芯片更快，而来自模拟对象的数量与它们之间的耦合：从「三颗各司其职的芯片」变成「一颗主 CPU 加若干协处理器加一块带内部状态的 GPU」，再加上光盘与多种外设。每增加一个部件，模拟器的状态空间与同步点就成倍上升。这也是为什么模拟器写作者常把「把 CPU 模拟对」称作通往其它一切的入口：CPU 一乱，上层的图形与音频再准也无从谈起。

## 6. 解释器、动态重编译与 HLE／LLE 的长期分歧

### 6.1 解释器

最直白的做法是解释器（interpreter）：取一条目标指令，翻译并在宿主上执行它的效果，再取下一跳。它结构清楚、便于调试，遇到未实现的边角行为也容易加日志。代价是每条指令都要经过一轮「取指—分派—执行」，速度往往是原生执行的几十分之一。对 8 位与 16 位主机，这点代价尚可承受；对 32 位及以上主机，纯解释器很快就撑不住帧率。

### 6.2 动态重编译

动态重编译（dynamic recompilation）把解释器的工作提前并缓存。模拟器维护一段「翻译缓存」，遇到一段尚未翻译的目标代码，就把它整段翻成宿主的机器码，之后重复执行这段代码时直接跳到缓存，省去逐条分派。更成熟的做法会记录目标寄存器的使用情况、做寄存器分配、把基本块串联成带分支的图。这一套与虚拟机的即时编译（Just-In-Time，JIT）本质相通，都是「边运行边把别人的代码译成自己的代码」。难点集中在自修改代码、精确异常与中断时机：游戏如果在运行中改写自己的指令，缓存就必须失效重译；如果异常发生的时刻与真机差一拍，某些程序就会走错。

RPCS3 的演变是这条路线的清晰样本。它在 2011 年以解释器起步，2014 年加上 PPU 与 SPU 的即时编译器，SPU 侧先用直接翻译到 x86 的方案，2018 年换成基于 LLVM 的方案，把函数作为一个整体分析、生成控制流图并减少多余的寄存器读写。到后来，ARM64 平台的即时编译又遇到新的问题：页面大小从 4KB 变成 16KB 后，靠脏页追踪来管理纹理缓存的机制代价明显上升。

### 6.3 HLE 与 LLE

高层模拟（High-Level Emulation，HLE）与低层模拟（Low-Level Emulation，LLE）的分歧，本质上是「在哪一层截断」。HLE 不去模拟硬件细节，而是识别程序对系统库的调用，直接用宿主代码实现同样功能。UltraHLE 是这条路线的标志性案例：它发现 Nintendo 64 游戏多用 C 编写，于是截住库函数调用并重实现，从而绕开整条图形微码。LLE 反过来，尽量把硬件与固件都照原样模拟，包括那颗 BIOS。

两者的取舍很具体。HLE 快，能在当年乃至现在的硬件上跑新主机，但兼容性依赖逐游戏适配，一旦某个游戏换了一种调用方式就可能失灵；UltraHLE 首发时能稳定玩的商业作品大约二十款，正是这一点的写照。LLE 通用、稳定、利于研究方法，但慢，而且常需要用户自备受版权保护的 BIOS。实践中，多数成熟的模拟器是混合体：CPU 侧倾向精确，图形与系统服务侧在 HLE 与 LLE 之间可切换。Dolphin 模拟 GameCube 与 Wii 时，就用 HLE 重实现 Wii 的系统服务，并对音频 DSP 提供 HLE 选项；这样既省去了用户自备固件的麻烦，也把「重实现」的风险限制在可控范围内。

### 6.4 分歧的后果

这条分歧线留下了两个后果。技术后果是，模拟器社区内部形成了一种以精度为荣誉的取向：一部分项目以「逐周期还原」为公开目标，宁可跑得慢，也要让依赖时序的卡带与自修改代码正常工作；另一部分项目以「让最多人能玩到最多游戏」为目标，接受逐游戏适配。社会后果是，HLE 与 LLE 的区别直接决定了「要不要自己准备 BIOS」这类玩家日常问题，也决定了模拟器与版权法之间的距离：越靠近 LLE，越容易触到受保护的固件；越靠近 HLE，越要面对「这还算不算模拟」的争论。

## 7. PS3 的 Cell、SPU 与 RSX：异构的代价

### 7.1 Cell 的结构

PlayStation 3 的主处理器 Cell Broadband Engine 由索尼、IBM 与东芝联合设计。它由一颗相对常规的 PowerPC 处理单元（PPU）与若干颗协处理单元（SPU）组成，各单元通过一圈高速内部总线相连。每个 SPU 拥有一块 256KB 的本地存储（Local Storage，LS）而不直接访问主存，要读写主存必须通过内存流控制器（Memory Flow Controller，MFC）发起直接存储器访问。SPU 擅长大规模单指令多数据运算，但内存访问要显式排队；MFC 支持乱序执行，也允许程序显式要求把某些传输挂起。

这套设计给游戏带来的收益是并行算力，给模拟器带来的负担则成倍上升。模拟 SPU，首先要模拟它的本地存储与通道接口——SPU 通过固定编号的读通道与写通道与外界通信，写通道可以发起 DMA，也可以写入邮箱，部分通道还带有原子语义；其次要模拟 MFC 的传输队列，包括乱序与挂起；最后还要处理非 IEEE 754 的浮点行为，比如把极值截断、把舍入方向固定。RPCS3 在 2017 年的一篇开发日志里提到，某些作品会在 SPU 的地址 0 处放一段分支代码，靠 SPU 的中断机制跳过去，而模拟器此前对中断的判定写错了；只有把这些行为补上，这些作品才能从黑屏推进到可玩。

### 7.2 RPCS3 的路线

RPCS3 由 DH 与 Hykem 于 2011 年 5 月发起，最初只是一个用 wxWidgets 写的 PS3 ELF 反汇编器，后来演变成模拟器。它早期的路线与多数同行相似：用户态 PPU 解释器、实验性 SPU 解释器、一套覆盖线程与同步、定时器、文件系统、图形与手柄的系统调用高层实现，图形侧用 OpenGL 与 GLSL 搭起来。2014 年前后，Cell 与 SPU 的模拟完善，让第一批商业作品进入可玩状态；2017 年引入 Vulkan 后端后，性能提升被官方口径形容为接近四倍；2021 至 2022 年间，项目把支持扩到 ARM64，先是靠解释器跑通样例，再逐步恢复即时编译。

这一路线的核心难题始终是「同步」。Sony 的图形处理器 RSX 由 Cell 通过命令队列驱动，两条流水线共享主存；模拟器必须决定何时让 GPU 侧停下来、把数据读回给 CPU，以及何时可以假设某块显存不会再被 CPU 访问。RPCS3 的开发者把这类操作分成上传与下载两类，上传可以批处理并异步隐藏延迟，下载则往往要让整条 CPU 线程等待，代价很大。项目因此默认关闭一部分缓冲选项，以减少这种硬停顿。

### 7.3 RSX 与着色器翻译

RSX 是基于 NVIDIA 当年桌面图形核心改制的，指令集与桌面 GPU 相近。模拟它的做法是把 RSX 的着色器程序翻译成宿主的着色器语言，再编译成 Vulkan 或 OpenGL 能执行的中间表示。难点在于编译器要花时间：一款游戏进入新场景时会遇到新着色器，宿主驱动需要几十到上百毫秒去编译，画面就会卡顿。RPCS3 的对策是异步翻译与「超级着色器」（ubershaders）：先把可能用到的一大类着色器预先编译，遇到新场景时用近似版本顶一下，等真正的编译完成再替换。

此外还有一类细节问题被反复记录：PS3 允许同一块内存既当颜色目标又当深度目标，仅凭地址与多重渲染目标配置无法判断用途，模拟器只能依赖更多上下文；某些指令会把三个未使用的位一起操作，导致亮度出现随机亮点；三十二位浮点常量在非 x86 平台上的解码需要另写分支。这些工作几乎无法靠「把指令表抄完」解决，只能逐款游戏向前推进。

### 7.4 异构难点的外溢

异构带来的负担并不止于模拟器作者。Digital Foundry 在 2022 年评测 RPCS3 运行《合金装备 4》时指出，Cell 的 SPU 算力是这台主机真正的特色，也是模拟器的最重负担：游戏用到的 SPU 越多，模拟所需的宿主 CPU 就越强。像《恶魔之魂》与《山脊赛车 7》这类对 SPU 依赖较低的作品跑得很好，而对 SPU 依赖高的作品即使在当代高端 PC 上也未必能稳定超过原机表现。这个结论也解释了为什么在当代主机上做官方 PS3 兼容并不轻松——要让上一代的异构算力在通用 CPU 上重现，代价不会因为时间推移而消失。

## 8. 从模拟器到虚拟化：QEMU、KVM、Hyper-V

### 8.1 两条技术路线

模拟与虚拟化的共同点，是都让一台机器「假扮」成另一台；区别在于指令怎么执行。模拟器把目标指令翻译成宿主指令，硬件不必同构；虚拟化让目标指令直接在宿主处理器上跑，只在必要时刻陷入由虚拟机监控器接管的特权操作。前者通用但慢，后者快但要求目标与宿主指令集相同、且处理器提供虚拟化扩展。

### 8.2 QEMU

QEMU 由 Fabrice Bellard 于 2003 年发布。它的 0.4 版在 2003 年 6 月的邮件列表公告里写明：可以直接启动未修改的 Linux 内核，并借助动态编译获得可接受的执行性能；当时它模拟了串口控制台与一块 NE2000 网卡，并能跑起 X11 程序。它的动态翻译器（后来称 Tiny Code Generator，TCG）把目标指令切成小块、翻译、缓存，再按需执行。QEMU 同时支持整机模拟与用户态模拟：前者跑一个完整操作系统，后者只跑某个目标平台的单个 Linux 程序。

Bellard 还写过一个名为 KQEMU 的 Linux 内核模块，让同构目标可以尽量直接执行、只把内核态与实模式交给模拟。它最初是免费但闭源的，2007 年 2 月起改以 GPL 授权，之后因与 QEMU 0.12.0 起的大内存支持不兼容而被移除。替代它的是一条更彻底的路：把虚拟化下沉到内核。到 2011 年 QEMU 发布 1.0 时，它已能模拟 14 种目标架构与四百多种硬件设备，并成为 Xen 与 KVM 这类平台的共同底座。

### 8.3 KVM

KVM（Kernel-based Virtual Machine，基于内核的虚拟机）的思路是把 Linux 内核本身变成 hypervisor：一个内核模块负责创建与运行虚拟机，借助处理器的虚拟化扩展（Intel VT-x 与 AMD-V）让客户机指令直接执行，只把敏感操作陷入内核处理。QEMU 在这条组合里扮演设备与机器模型的角色，KVM 负责执行。KVM 由 Avi Kivity 于 2006 年在 Qumranet 公司启动，次年并入 Linux 主线内核，2008 年 Qumranet 被红帽收购。此后，KVM 与 QEMU 的组合成为 Linux 上硬件辅助虚拟化的主流方案。

### 8.4 Hyper-V、VMware、VirtualBox 与 Xen

微软的 Hyper-V 于 2008 年随 Windows Server 推出，采用「微内核化」的结构：一层很小的 hypervisor 之下是若干分区，管理分区拥有大部分设备驱动，客户分区按需获得资源。VMware 更早，1998 年由 Diane Greene、Mendel Rosenblum 等人创办，1999 年推出工作站产品，随后把同一套技术做成服务器产品；它早期靠二进制翻译在尚未普及虚拟化扩展的 x86 上实现虚拟化，后来转向硬件辅助。VirtualBox 由 InnoTek 于 2007 年发布，2008 年被 Sun 收购，2010 年随 Sun 并入甲骨文。Xen 于 2003 年在剑桥大学成形，早期以半虚拟化著称——要求客户机操作系统做少量修改，以配合 hypervisor，后来也支持硬件辅助的全虚拟化。

### 8.5 设备模型、机器描述与迁移

QEMU 与家用机模拟器还有一处结构差异。家用机模拟器面对的是固定硬件：一台 NES 就是那几颗芯片，模拟器只需把这套规格实现一遍。QEMU 面对的是「任意一台 PC」，于是它把硬件拆成可组合的部件——处理器型号、芯片组、内存、磁盘控制器、网卡、显示设备各是一段可插拔的描述，用户挑一套拼出一台虚拟机器。这种「机器描述」的思路让同一套软件既能模拟十年前的主板，也能模拟最新的平台，也让虚拟机可以在不同宿主之间迁移：把机器状态搬过去，它就能在另一台物理机上接着跑。

设备直通是同一思路的另一面。虚拟设备由软件模拟，速度与功能都受限；把一块物理显卡或网卡直接交给某台虚拟机使用，性能接近原生，代价是牺牲了部分隔离与迁移能力。围绕这些问题，后来发展出专用的虚拟设备接口、嵌套分页与中断直通等机制。与家用机模拟相比，这里的复杂度不在「把一台机器算准」，而在「在运行时动态地把机器的边界挪来挪去」。

### 8.6 概念边界

把这条线讲清楚，需要把几个层面的东西分开。虚拟机监控器是实现「一台物理机同时承载多台虚拟机」的那层软件；它既能被数据库、企业软件与开发者用来做整合与测试，也能被个人用来在 Linux 上跑一个 Windows。这些需求在 2003 到 2008 年是真实存在且具体的：服务器利用率偏低、内核开发需要反复重启、跨平台开发需要一台机器跑多个系统。至于把虚拟化描述成「云」或「容器」的前身，则是后来的叙事——容器共享内核、更接近进程隔离，云是另一层编排与计费模型，它们都借用了虚拟化打下的地基，却不是当初的出发点。

同一条线索里，模拟器与虚拟化还共享了一批人。写模拟器的人惯于维护「机器状态」与「精确时序」，这些技能在虚拟机、设备模型与测试环境里同样吃香；反过来，虚拟化把「可复现的机器」变成了工程常规，也间接推动了后来用模拟器做回归测试与固件分析的做法。

## 9. 兼容层与模拟器的边界：Wine、Proton、DXVK、vkd3d-proton

### 9.1 Wine 的起点

Wine 于 1993 年在 comp.os.linux 的讨论里起步，最初的动机很具体：Sun 已经做过一套在 Unix 上运行 Windows 程序的方案（WABI），Linux 用户也希望有同样的东西。Bob Amstadt 写下了最初的加载器，让 Windows 可执行文件能被读入内存并正确修正地址；此后项目长期由 Alexandre Julliard 主持。它走的是与家用机模拟器相反的路线：不去模拟 x86 指令——那些指令本来就由同一颗 CPU 直接执行——只把 Windows 的 API 与调用约定翻译成 POSIX 与 X11 的调用。这个名字本身就是一句口号：Wine Is Not an Emulator。

早期的进展可以按年计：1993 年先把加载器搭起来，Windows 自带的纸牌勉强能玩；1996 年加上 Win32 支持；1997 年 Word 95 能启动。这样一条「逐年补 API」的路线走了十五年，直到 2008 年才发布 1.0 稳定版。它的长处是性能：程序代码原生执行，没有指令翻译的开销；短处也很清楚——Windows 的 API 面极广，还有大量未公开行为，缺一项就可能让某个程序起不来。

### 9.2 Proton

2018 年 8 月，Valve 发布 Steam Play 的 Proton，并说明这是与 CodeWeavers 合作、私下开发了两年多的成果。Proton 以某个版本的 Wine 为基础，附上一批为游戏专门准备的组件：Direct3D 到 Vulkan 的翻译层、OpenVR 与 Steamworks 的原生接口桥接、针对多线程的 esync 补丁集，以及与 Wine 一同演进的音频与 .NET 实现。首发时 Valve 内部验证了二十多款传统与虚拟现实游戏，涵盖《毁灭战士》系列、《尼尔：机械纪元》与《雷神之锤》一类；其余游戏可以通过一个开关手动尝试。

Proton 与纯 Wine 的差别，落在「默认面向游戏」这件事上：全屏切换、多线程调度、手柄支持都被专门处理过。Valve 后来公布的数字显示，Proton 自身的改动之外，大量修复都回流到了上游 Wine。到 2019 年，Proton 从基于 Wine 3.7 迭代到基于 Wine 4.11，两者之间的 Wine 改动接近八千条。2021 年 Steam Deck 发布，兼容层第一次成为一款量产掌机运行 Windows 游戏的默认方式。

### 9.3 DXVK 与 vkd3d-proton

Steam Play 能成立，一半功劳要归于图形翻译。DXVK 由 Philip「doitsujin」Rebohle 于 2018 年 1 月公开发布，把 Direct3D 8 到 11 的调用翻译成 Vulkan。它的起点很个人化：作者想在一块 AMD 显卡上玩《尼尔：机械纪元》，既不满意 Wine 自带的 Direct3D 11 到 OpenGL 的性能，又受驱动问题困扰，于是干脆自己写一条到 Vulkan 的翻译路径。发布后不久，Valve 便把他聘为合同开发者。此后 DXVK 持续换代，陆续加上对 Direct3D 9、HDR、Direct3D 8 的支持，并逐步收紧对 Vulkan 版本的要求。

Direct3D 12 一侧，上游已经有了 vkd3d。2020 年 7 月，Valve 的 Hans-Kristian Arntzen 把它分叉成 vkd3d-proton，公开的目标是优先性能与游戏兼容，胜过对旧驱动的兼容，并积极使用较新的 Vulkan 扩展。此后 DXVK 与 vkd3d-proton 成了 Proton 里负责图形的那两只手。

### 9.4 边界与代价

兼容层与模拟器的边界在两处容易被混淆。第一处是「要不要模拟指令」：在 x86 主机上跑 x86 的 Windows 程序，Wine 只做 API 翻译，指令原生执行；只有在不同指令集的宿主机上（例如某些 ARM 设备），才需要再叠一层指令翻译。第二处是「谁负责图形」：Wine 自带 wined3d，把 Direct3D 翻成 OpenGL，DXVK 则翻成 Vulkan，两条路径在不同年代各有拥趸。反过来，家用机模拟器走的是「模拟整台机器」，兼容层走的是「只翻译系统与图形接口」，两者解决的问题并不相同，只是都让「别人的软件在自己的机器上跑起来」。

代价也很具体。反作弊与数字版权管理程序往往要访问内核接口、依赖未公开行为，兼容层很难照单全收，这类游戏至今常被排除在外。兼容层还依赖宿主驱动与图形栈的质量，早期常见的着色器编译卡顿就一直困扰玩家。到 2020 年代，兼容层已经从「折腾人的玩具」变成消费设备的默认选项，但它的边界依然由这些底层约束划出。

## 10. 掌机、手机与街机：三类不同的模拟对象

### 10.1 掌机

掌机的模拟对象看似简单，实则各代差异很大。Game Boy 用的是接近 8080 的处理器，屏幕是特殊的点阵，靠一块可切换的存储体管理图形，把它模拟出来相对轻；面向它的模拟器从 1990 年代中期就出现，后来在 PC 与手机上成了最常见的品类之一。Game Boy Advance 换成 32 位 ARM 内核，还带一套向后兼容的图形模式；Nintendo DS 干脆是双屏双处理器，下屏带触摸。PSP 用 MIPS 内核加一块带硬件变换的图形单元，模拟器要在手机等低功耗设备上兼顾性能。到了 Nintendo 3DS 与 Switch，模拟对象已是多核异构加现代 GPU，难度回到与家用机同一量级。掌机还有一层特殊约束：屏幕小、按键少，模拟器要自己设计触摸、虚拟摇杆与存档方式，玩家的手感与原机并不相同。

### 10.2 手机与安卓

手机上的「模拟器」有两种很不一样的形态。一种是真正的掌机与家用机模拟器，把 PSP、GBA、NDS、PS1 等平台的游戏搬到手机上，靠触屏或外接手柄操作；另一种是把为 ARM 编译的安卓应用跑在 x86 设备上，靠一层指令翻译来执行，严格说更接近「应用兼容层」。后一类在 2010 年代随安卓平板与 PC 上的移动游戏需求而流行起来，也促成了厂商在文件管理、多点触控与图形合成上做专门适配。手机的算力与散热长期是限制条件，模拟器作者因此更在意省电与降频表现。

### 10.3 街机

街机模拟像另一门学问，根本原因在于它的对象是几千台各不相同的机器。每块基板都有自己的主 CPU、图形芯片、声音芯片、输入设备与控制协议，从赛车框体的方向盘到光枪、轨迹球、转盘，几乎没有通用规格。街机模拟器因此采用「逐基板驱动」的写法：每一款游戏对应一段驱动代码，精确描述这块基板的芯片、内存映射、时序与保护机制。这种结构决定了街机模拟的进度是「一款一款拿下的」，而不是「一换代就全覆盖」。

MAME 正是这一路线的代表。它从 1997 年复现《吃豆人》的小程序起步，在两年内扩成能跑数百款街机游戏的系统，由意大利学生 Nicola Salmoria 牵头。它与被模拟的厂商之间长期处于紧张关系：1999 年，行业组织 IDSA 曾要求网络服务商撤下街机 ROM 文件；而 MAME 团队把自己的工作定位成硬件档案——Salmoria 说过，MAME 是「世界上最大的街机硬件文档集合」，并强调如果不去保存，五十年后基板会损坏到无法修复，那时没人能替它们做这件事。到 2015 年，MAME 与家用机模拟项目 MESS 合并，把家用机的驱动也纳入同一套代码库，方向仍是「把硬件行为记录下来」。

街机的另一重难点在介质。很多基板的 ROM 芯片、可编程逻辑器件与音频取样需要专门的读取设备才能完整转储，部分芯片还有保护电路，需要在运行中绕过或还原。这些工作的成果是一份可校验的硬件描述，而不是可玩的游戏文件；模拟器本身通常不附带 ROM，玩家要自己准备。把街机放进本文的线索里，它代表的是那类「必须逐机器、逐器件做工程」的对象——与「一次写对就通吃一个世代」的家用机模拟形成对照。

## 11. 插件时代与后端战争

### 11.1 插件为什么出现

1990 年代末到 2000 年代中，PC 显卡的形态极度分散：有的只做二维加速，有的靠 Glide 接口做三维，有的是刚起步的 Direct3D 与 OpenGL 实现。PlayStation 的三维画面要落到这些硬件上，没有一套统一走法，于是模拟器把「输出」这件事拆成插件：图形插件负责把画面渲染出来，音频插件负责声音，光驱插件负责读盘，输入插件负责手柄。同一套模拟核心可以配不同的插件组合，玩家按自己的显卡与偏好挑选。为了让不同模拟器之间可以互换插件，早期社区事实上形成了一套共同的接口约定，后来的项目沿用或改写它，这也是同一块显卡插件能被多款模拟器识别的由来。

Nintendo 64 一侧的情形更极端。它的图形管线由可编程微码驱动，早期模拟器为了在非 3dfx 显卡上运行，专门出现了把 Glide 调用转成 Direct3D 的封装层——游戏面向的是 3dfx 的 Glide，封装层再把 Glide 转给别的显卡。这类「转换层」的思路后来在别处反复出现，只是换了名字与对象。

插件模型的代价同样明显：配置项繁多、版本组合复杂，一个插件与另一插件的搭配可能决定游戏能否正常显示。对当年的玩家，这构成了一段具体的记忆——装完模拟器第一件事是找插件、调分辨率、试各种组合，直到画面不再抖动或不再缺字。

### 11.2 图形后端的迁移

图形后端的更替贯穿了这段历史。Glide 随 3dfx 显卡的兴衰退场，Direct3D 与 OpenGL 成为两大主流；模拟器逐渐把「软件渲染」与「硬件渲染」两种后端都纳入选择，前者还原度高、后者能提升分辨率与纹理过滤。进入 2010 年代，Vulkan 出现，给了模拟器一条更贴近现代驱动、开销更低的路径：RPCS3 在 2016 年引入 Vulkan 后端，DXVK 与 vkd3d-proton 也把 Vulkan 当作翻译的目标。分辨率的提升顺带改变了模拟器的意义——它让老游戏能以远高于原机的清晰度呈现，这一度是玩家使用模拟器的重要理由，也带来了与原机画面不符的争议。

### 11.3 整合与统一

随着显卡形态收敛，独立插件模型的收益下降。新一代模拟器更倾向于内置多种后端，由用户在设置里切换，而不要求去外部寻找插件；RetroArch 这类前端则用「核心」的方式把大量模拟器统一到一套界面与手柄映射之下，把插件的思路改造成「换核心」。到 2020 年代，插件的黄金时代基本过去，但它在同一段历史里留下了两个成果：一是把「模拟核心」与「呈现方式」解耦的做法，二是由此形成的玩家技术文化——会调参数、会比画面、会在论坛里互相报版本。

## 12. ROM、BIOS、固件与 dumping 的介质和来源

### 12.1 卡带与光盘

模拟器需要「数据」，而数据的来源是介质转储（dump）。卡带类介质要用专用读取设备把 ROM 芯片内容完整读出来，早年出现过能在主机上做备份的适配器与烧录卡，后来也有面向收藏者的通用读取器。光盘类介质要在 PC 光驱上把整盘数据与子通道信息一起抓取，保存成带描述的镜像；不同主机对扇区、音轨与保护区的处理各不相同，镜像格式也因此分化。

### 12.2 BIOS 与固件

不少主机的启动过程依赖一段厂家固件。PlayStation 一类的机型，其 BIOS 在低层模拟（LLE）路线下是必需的；PlayStation 3 的官方固件可以安装进 RPCS3 以提供更完整的系统环境；掌机世代还牵涉到加密密钥与系统分区。厂商固件受版权保护，模拟器通常不附带，玩家需要从自己的机器上提取。这条边界既是法律上的，也是工程上的：越依赖固件，模拟器越难做到「开箱即用」。

### 12.3 校验数据库与格式

为了让转储结果可信，社区建立了校验数据库：把每一个 ROM 或镜像的唯一哈希与名称对应起来，区分「正确转储」「存在误差的转储」与「被修改过的版本」。卡带镜像有各自的扩展名，光盘镜像也有多种容器格式，其中一类把整盘数据压缩并附带索引，兼顾体积与随机访问。这些格式与数据库构成了模拟器与保存工作之间的接口：模拟器按校验值判断数据是否完整，保存者按校验值确认自己的转储是否可长期引用。

### 12.4 来源与合法性

模拟器本身通常不提供游戏数据，数据的获取与传播处在法律灰区。判例给出的边界主要在「为开发模拟器而复制固件是否属于合理使用」，而不在「下载并分发游戏文件是否合法」。1999 年前后，行业组织对街机 ROM 网站的要求下架、对模拟器作者的诉讼威胁，构成了这段历史的另一条线。对普通玩家而言，这段历史留下的经验很直白：模拟器是工具，数据要自己准备，而工具与数据之间那条线，正是后来所有争议的源头。

## 13. 数字保存、逆向工程与研究价值

### 13.1 硬件会坏，保存是和时间赛跑

游戏史的物质基础并不牢固。卡带的电池会漏液，光盘会氧化，街机基板会因电容老化而失效，磁带与软盘更脆弱。MAME 团队把这一点说得最清楚：如果不去保存，基板迟早会损坏到无法修复，到那时就没有人能替它们做这件事了。保存工作的成果落在一份份可校验的数据、扫描图与硬件描述上——它们让后人在原件消失后仍能研究当年的设计。家用机与街机的模拟器，正是在这个意义上从怀旧工具长成了保存工具。

### 13.2 逆向工程与判例

模拟器要理解一台机器，往往必须逆向工程。这里有两份被反复引用的判例。其一是 1990 年代初世嘉与 Accolade 的纠纷，法院认定为了获取程序中的功能要素而反汇编属于合理使用；其二是 Sony 与 Connectix 的纠纷，联邦第九巡回上诉法院在 2000 年判定，Connectix 为开发 Virtual Game Station 而复制索尼 BIOS 属于合理使用，因为不复制就无法接触到其中的功能要素。判决同时指出，反向工程过程中的中间复制受保护，并不因为最终产品里没有索尼代码而失去意义。这两份判决给模拟器与兼容性开发留出了空间，也正是它们让后来的兼容层与备份工具在法理上有了依据。

需要与「下载游戏是否合法」区分开：这些判例处理的是「为开发互操作产品而复制固件」这件事，并不能推导出「分发游戏镜像合法」。把两者混为一谈，是这段历史里最常见的误读。

### 13.3 官方模拟与再发行

被模拟对象的所有者，后来也走上了模拟这条路。任天堂在 Wii 时代推出虚拟主机，把老游戏按平台重新发售；此后又推出迷你复刻机、订阅制的经典游戏库。索尼在后续主机上提供 PS1 与 PS2 兼容，并通过订阅目录重新发行旧作；微软用一套逐游戏适配的兼容方案把上一代主机的作品搬到新主机上。官方方案在画质、存档与联机上做了自己的一套处理，也以另一种方式回应了「旧作保存」的需求。玩家社区对此的讨论，大多集中在可用作品范围、画面改动与购买方式上，而不是「官方模拟器是否算模拟器」。

### 13.4 中国玩家的模拟器记忆

在中国，模拟器的普及早于正版主机的大规模流通，这条线因此格外具体。红白机时代，市场上流通的多是克隆机，其中以「学习机」名义销售的机型把主机做成带键盘的盒子，卡带则以黄色外壳的合卡为主，一张卡里塞进多款游戏。再往后，带游戏功能的影碟机把红白机游戏塞进客厅，用一个手柄就能玩到与家用机同源的作品，这在 PC 尚未普及时是很多家庭的第一次接触。

PC 普及之后，记忆转向「找软件」这件事。街机厅里的格斗与横版过关作品，通过一系列支持 CPS 与 Neo Geo 的模拟器进入家用电脑，网吧里常能见到围绕这些模拟器建立的游戏区；家用机侧，玩家习惯的是先装模拟器、再去论坛或网站找 ROM 与 BIOS，然后面对一长串插件与配置项反复试错。掌机模拟器让很多人在没有掌机的情况下玩到了 GBA 与 NDS 的作品，汉化组则在这些工具之上做出中文版本，让不熟悉原文的玩家也能读懂剧情。金手指、即时存档、加速与倒带，逐渐成了这一代玩家对「模拟器」的默认期待。

随着智能手机普及，这段记忆又搬到手机上：有人用掌机模拟器在通勤路上补完少年时没玩完的作品，有人用整合了多个平台的第三方前端把它们装进一个图标，也有人只是偶尔打开一个街机模拟器，听一段当年的开场音乐。对一部分玩家来说，模拟器是当年唯一够得着的入口；对另一部分玩家来说，它是把旧作放到今天设备上重看的工具。这两重身份，正是本文所说的「怀旧工具」与「保存与研究工具」在中国语境里的合流。

### 13.5 研究用途与可复现实验

模拟器在学术与工程上的用途，常被怀旧叙事掩盖。它最直接的价值是「可复现」：一台被软件重现的机器可以被随时暂停、保存状态、逐条回放，而真机不行。速通验证正是靠这一点成立的——工具辅助速通把游戏分解成可回放的输入序列，用模拟器逐帧重放，从而把「这一帧按下了什么」变成可比较的数据。要做到可比较，模拟器就必须在相同输入下给出相同结果，这反过来推动了逐周期精确这一取向。

第二类用途是把模拟器当成探测器。研究者可以在模拟环境里监控一次固件更新或一次设备初始化过程中，哪些地址被读写、哪些信息被送往外设，从而在不改动真机的前提下观察黑盒行为。这类用法在嵌入式与安全领域后来变得常见，它的技术底子与家用机模拟器同源：先描述机器的状态，再在可控环境里推进它。用它来改写设备行为、绕过保护，则是另一回事，本文不作展开。

第三类是教学与架构比较。把同一款程序放在两个不同架构的模拟器里运行，或把同一台机器的两种实现并列比较，可以让抽象的指令集、流水线与内存层级变成可观察的对象。高校的体系结构课程里，用模拟器讲解流水线、缓存与中断，与用家用机模拟器讲解图形芯片的扫描线，方法上是一回事。到了游戏研究领域，模拟器又成了文本比较与版本考据的工具：同一款作品在不同区域、不同版本里的差异，可以在被固定住的机器上逐帧比对。

这些用途合起来说明了一件事：模拟器把「机器」从一件具体的、会坏的、买不到的物，变成了可以在软件里反复调用的对象。数字保存保住了它的数据，逆向工程保住了它的结构，而模拟器保住了它的运行。三者叠起来，才是「旧游戏还能被研究」这件事的完整条件。

## 14. 一句话总结

模拟器与虚拟化时代是电脑逐步学会在自身内部重现别人的处理器、图形、总线与系统服务的历史，它从让人在 PC 上玩到红白机起步，经超任、PlayStation、N64，一直到 PS3 的异构 Cell、现代 GPU 的图形翻译与 hypervisor 时代的整机虚拟化，最终把一件为怀旧而生的工具，做成了数字保存、兼容层与计算基础设施的一部分。
