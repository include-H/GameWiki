# 虚拟化技术分层与谱系

> 说明：本文是针对"虚拟化"这一组概念的辨析性整理，写作重点是把 Type 1 与 Type 2、全虚拟化与半虚拟化、裸金属型与宿主型、薄 hypervisor、容器与虚拟机的区别、以及 WSL2 为什么算虚拟机，放进同一张分层图里。整理对象从 1960 年代 IBM 的 CP/CMS 一直延伸到 2018 年前后的 microVM，覆盖 hypervisor 术语的来源、x86 上三种虚拟化路线的取舍、OS 级虚拟化与机器级虚拟化的分界，以及中文语境里的网吧无盘、还原软件与安卓模拟器。主要依据为厂商官方文档与研究论文（IBM、VMware、Xen 项目、Linux 内核与 QEMU 文档、Microsoft Learn、AWS 官方博客），辅以 Wikipedia、USENIX / ACM 论文与专业媒体。术语一律保留英文原文。文中日期与版本号以可核查来源为准，来源之间冲突或口径不一的地方标注「待核实」。检索时间：2026 年 10 月 18 日。

## 一、先分清四组词：虚拟化、模拟、分区、容器

"虚拟化"在日常中文里被用作一个统称，范围大到把模拟器、双系统、云端容器、安卓模拟器都卷了进来。要谈分层，先把四组含义相近的名词拆开。

**虚拟化（virtualization）** 指在真实硬件之上插入一层软件，把物理资源切分或合并成若干个"看起来像独立机器"的执行环境，让原本直接操作硬件的一层软件（通常是操作系统内核）改而操作这层虚拟硬件。它有一个常被忽略的效率前提：大部分非特权指令必须在真实 CPU 上直接执行，只有少数会破坏隔离的指令才被拦截并模拟。Gerald J. Popek 与 Robert P. Goldberg 在 1974 年的论文《Formal Requirements for Virtualizable Third Generation Architectures》里把这一点写成"效率要求"，正是这条要求把虚拟化与后面要说的模拟区分开来。

**模拟（emulation）** 指在一个指令集上逐条翻译并执行另一个指令集的程序语义。QEMU 在不加载 KVM 加速时就是以动态二进制翻译（dynamic binary translation, DBT）的方式运行，翻译块被缓存进 translation cache，重复执行时跳过翻译步骤。模拟可以跨架构——在 x86 主机上跑 ARM 或 PowerPC 系统——而虚拟化按定义要求 guest 与 host 同架构，否则"非特权指令直接在硬件上执行"这条前提无法成立。同一款 QEMU，加了 `-accel kvm` 是虚拟化，不加就是模拟，这条界线在日常讨论里经常被抹掉。

**分区（partitioning）** 指在固件或硬件层面把一台物理机器切成若干独立运行环境，各环境有各自分配到的处理器、内存与 I/O。IBM 大型机上的逻辑分区（LPAR）与 PR/SM 属于这一路。分区环境之间通常不能共享内存，划分由机器控制台配置，属于比 hypervisor 更靠近硬件的一层。

**容器（container）** 指在同一个操作系统内核之上，用命名空间（namespace）与控制组（cgroup）把一组进程的可见资源与可用资源限制起来，让它们各自看到一个独立文件系统、独立进程号空间与独立网络。容器内的进程调用系统调用时直接进入宿主内核，中间没有虚拟硬件这一层。这一支在英文文献里叫 OS-level virtualization（操作系统级虚拟化），与 machine-level virtualization（机器级虚拟化）并列。

四者可以叠放：一台宿主机可以跑若干虚拟机，每个虚拟机里再跑几十个容器；同一台机器也可以用虚拟化跑一个 Linux，再用这个 Linux 跑容器。分层的意义在于判断一个问题究竟落在哪一层，而不是争论谁"更虚拟"。

## 二、源头：1960 年代的 CP/CMS 与 hypervisor 这个词

虚拟化最早的落地场景是大型机的分时共享。1960 年代初，IBM 一方面要守住科学计算市场，另一方面已经押上巨额资源开发 System/360，分时系统 CTSS 与 MIT 的 Project MAC 又抢走了注意力。为在 System/360 上验证分时方案，IBM 在麻省剑桥的 Cambridge Scientific Center（CSC）先后做了两台研究机：M44/44X 采用部分虚拟化（partial virtualization），只虚拟部分硬件接口；紧接着的 CP-40 实现了全虚拟化（full virtualization），把硬件的"监督态"（supervisor state）也一并虚拟化，使多台操作系统能在彼此独立的虚拟机上并发运行。CP-40 于 1967 年 1 月进入生产使用。

CP-40 随后被重写为 CP-67，跑在 IBM System/360 Model 67 上，这台机器带动态地址转换（DAT）与虚拟内存支持。1967 年 CP-67 与 CP-40 先后进入生产使用，CP/CMS 系统开始被 IBM 内部与 MIT Lincoln Laboratory 等外部站点日常使用。这套系统由两部分组成：CP（Control Program）负责创建虚拟机环境，CMS（当时叫 Cambridge Monitor System，后改称 Conversational Monitor System）是一个轻量单用户操作系统。CP/CMS 于 1968 年被放进 IBM 的 Type-III Library，以源代码形式提供给客户，不含官方支持。这种"自己搭、自己修"的分发方式催出了早期用户社群，到 1972 年 CP-67 已在 44 台处理器上运行，单台 S/360-67 可支撑 60 个 CMS 用户，National CSS 与 IDC 两家公司靠转售基于 CP/CMS 的分时服务起家。

IBM 官方在 1972 年 8 月 2 日随 System/370 Advanced Function 公告发布了 VM/370，这是 CP/CMS 面向 S/370 的重实现，也是这款技术第一次作为正式产品交付。

"hypervisor"这个词本身出现得比 CP/CMS 的商业化略晚。按 Wikipedia 与 IBM 资料的说法，该词约在 1970 年前后由 IBM 使用，最初指在 360/65 上同时运行 OS/360 与 7090 模拟器的软件，后来被用于 CP-67 处理 DIAG 指令的处理程序。在 CP/CMS 时期的文献与代码里，对应的名字是 Control Program。1974 年 Popek 与 Goldberg 的论文把 "hypervisor" 列为关键词之一，但正文使用的是 VMM（virtual machine monitor）。

Type 1 与 Type 2 这组分类来自 Robert P. Goldberg 1973 年的博士论文《Architectural Principles for Virtual Computer Systems》。论文把 hypervisor 分成两类：直接跑在硬件上、自己管理硬件的 Type-1（又称 native 或 bare-metal），以及跑在常规操作系统之上、作为普通程序运行的 Type-2（又称 hosted）。这一分类后来被反复引用，IBM 在 1960 年代开发的测试软件 SIMMON 与 CP/CMS 被归入最早的 native hypervisor。

这一整段历史有一个必须点明的边界：1960 至 1970 年代的虚拟化解决的是分时共享计算机时间，以及让老程序在新机器上继续运行。它面对的用户是同一机构内部的程序员与操作员，面对的问题是如何把一台昂贵主机的时间卖给不同课题组。把它读成"云计算的起点"、读成"多租户安全的雏形"，属于后来概念的倒灌，本文在第十二节会专门列出这一类误读。

## 三、分层的坐标：控制点、共享粒度、隔离边界、guest 是否知情

要给散落的名字排出谱系，需要几根可比较的坐标轴。以下五根最实用。

**控制点**，即谁在管理这台机器。取值从小到大依次是：机器固件（IBM 大型机的 PR/SM、Amdahl 的 MDF）、直接跑在硬件上的 VMM（ESXi、Xen、Hyper-V 的 hypervisor 层）、宿主内核里的模块（KVM、bhyve）、宿主操作系统之上的普通进程（VMware Workstation、VirtualBox、不带 KVM 的 QEMU）、以及宿主内核本身（容器）。控制点决定了这层软件能看到多少真实硬件、出故障时影响范围有多大。

**共享粒度**，即被切分或复用的对象是什么。机器级虚拟化切分的是虚拟硬件：vCPU、虚拟内存、虚拟磁盘与虚拟网卡，guest 拿到的是"机器"。操作系统级虚拟化复用的是同一个内核：容器共享系统调用入口、调度器与驱动，只被限制"能看到什么"。

**隔离边界**，即隔离靠什么机制保证。虚拟机依赖 CPU 的虚拟化扩展（Intel VT-x 的 VMX root / non-root 模式、AMD-V 的 SVM）与 VM exit，guest 执行敏感指令时陷入 hypervisor；容器依赖命名空间加 cgroup，再加 seccomp、capabilities、SELinux/AppArmor 这类加固，隔离面是内核提供的资源视图。

**guest 是否知情**，即 guest 是否需要为"被虚拟化"做修改。全虚拟化下 guest 不知情，无需改动；半虚拟化下 guest 知情，通过 hypercall 这类接口主动配合；硬件辅助虚拟化下 guest 通常不需要改动，硬件模式负责把敏感操作交回 VMM。

**目标**，即这套东西当年要解决的原始问题：分时共享、旧程序兼容、服务器整合、交付一致性、多租户隔离。同一层技术在不同年代被用来解决不同问题，谱系因此更像一张随时间延展的地图。

大型机一侧的硬件分区史可以为"控制点"这根轴提供参照。IBM 从 1976 年起在纽约 Poughkeepsie 研究 S/370 架构上的逻辑分区，项目证明概念可行；Amdahl 在 1982 年推出 Multiple Domain Facility（MDF）；IBM 在 1983 年随 370-XA 架构在 IBM 3081 上引入 Start Interpretive Execution（SIE）指令，专门用于执行虚拟机，VM/XA 系列随即利用它；1988 年 IBM 在 ESA/370 架构的 IBM 3090 上推出 PR/SM（Processor Resource/System Manager），把逻辑分区做成产品功能，LPAR 从此随 System z 一路延续。按 IBM 文档，PR/SM 是划分硬件的固件与硬件组合，LPAR 是它产生的结果，这个区分在讨论中常被合并使用。早期大型机的 LPAR 数量上限为 15，后续机型扩到 30 以上。这段历史说明"控制点下沉到固件"并不是 2000 年代的新发明，IBM 在三十多年前就把 hypervisor 的一部分职责固化进了硬件。

| 判别维度 | 要回答的问题 | 常见取值 |
| --- | --- | --- |
| 控制点 | 谁在管理机器 | 机器固件 / 裸金属 VMM / 宿主内核模块 / 宿主 OS 上的进程 / 宿主内核本身 |
| 共享粒度 | 共享的是什么 | 虚拟硬件（整台机器） / 同一个内核的系统调用与文件系统 |
| 隔离边界 | 隔离靠什么 | 虚拟化硬件 + VM exit / namespace + cgroup |
| guest 是否知情 | guest 是否需要改动 | 全虚拟化（不知情） / 半虚拟化（知情） / 硬件辅助（通常不知情） |
| 原始目标 | 当年要解决什么 | 分时共享 / 旧程序兼容 / 服务器整合 / 交付一致性 / 多租户隔离 |

## 四、Type 1 与 Type 2：分类来源与模糊地带

教科书式的划分很干净。Type-1 hypervisor 直接运行在宿主硬件上，自己管理硬件并调度 guest 操作系统，典型代表是 VMware ESXi、Xen、Microsoft Hyper-V。Type-2 hypervisor 作为应用程序运行在常规操作系统之上，典型代表是 Oracle VirtualBox 与 VMware Workstation。Type-2 的额外延迟来自多出来的一层：设备请求要先经过宿主操作系统的调度与驱动路径，才能落到硬件。

这条界线在真实产品里并不总是一分为二。KVM 与 FreeBSD 的 bhyve 都是内核模块，加载后把宿主内核本身变成 hypervisor，Wikipedia 的 hypervisor 条目直接写明"两者的区分并不总是清晰"。Hyper-V 被微软归为 Type-1，但它的架构里必须至少有一个运行 Windows 的根分区（root partition，也叫 parent partition），虚拟化管理栈、虚拟交换机、存储与 PCI 的虚拟化组件都跑在这个根分区里，子分区通过 VMBus 与根分区通信；按 Microsoft Learn 的说法，根分区本身就是"一个有特权的 guest VM"。历史上 VMware 的 ESX 也不是完全没有操作系统：早期的 ESX 先启动一个 Linux 内核，再由它加载 vmkernel，那个 Linux 服务控制台（Service Console）后来在 ESXi 3.0（2008 年）中被移除，此后的 ESXi 完全不含 Linux 内核。

性能推论更不能一刀切。Type-1 省掉一层宿主 OS，通常在 I/O 密集与高密度场景占优；Type-2 的价值在部署简单、随宿主系统一起打补丁、便于开发与测试。把 Type-1 一律视为"快"、把 Type-2 一律视为"玩具"，会漏掉不少反例，比如在早期硬件辅助尚不成熟时，经过精心优化的软件方案在部分负载上反而更快（参见第五节）。

## 五、x86 上的三条路线：二进制翻译、半虚拟化、硬件辅助

x86 架构从 1978 年诞生起就不满足 Popek 与 Goldberg 提出的虚拟化条件。John Scott Robin 与 Cynthia E. Irvine 在 2000 年 USENIX Security 的论文《Analysis of the Intel Pentium's Ability to Support a Secure Virtual Machine Monitor》中逐条分析了 Pentium 的指令集，列出 17 条"敏感但非特权"（sensitive, unprivileged）的指令，例如 SGDT、SIDT、SLDT、SMSW、PUSHF、POPF、LAR、LSL、VERR、VERW，以及 CALL FAR、JMP FAR、INT n、RETF、STR 与读写段寄存器的 MOV。这些指令在用户态不触发异常，VMM 无法从陷入中得知 guest 执行了它们，trap-and-emulate 这条路被堵住。Wikipedia 同一主题的条目在统计条数时写作 18 条，两处口径不一致，具体条数「待核实」，但"x86 存在一批敏感非特权指令"这一事实有多篇论文与 VMware 官方技术文章互证。

为避免这些指令造成语义偏差，x86 上先后走了三条路。

**二进制翻译。** VMware 在 1999 年发布 Workstation 1.0（1999 年 5 月 15 日）时采用了混合方案：guest 的用户态代码与大部分指令直接执行，guest 内核中那些会破坏隔离的指令由系统级动态二进制翻译器在运行时改写，改写结果缓存在地址空间尾部的翻译缓冲里。相关技术原理公开于 Devine、Bugnion 与 Rosenblum 1998 年的美国专利 6,496,847《System and method for virtualizing computer systems》。VMware 的翻译器只做 x86 到 x86 的翻译，目标明确、结构紧凑，不追求跨架构能力。

**半虚拟化。** 剑桥大学计算机实验室的研究项目 Xen 走了另一条路：不假装自己提供完整的 x86 接口，而是要求 guest 操作系统做少量改动，用 hypercall 取代那些难以虚拟化的架构特性，在内存管理、CPU 与设备 I/O 三块上重新定义接口。Xen 于 2003 年首次公开发布，论文《Xen and the Art of Virtualization》发表于当年 10 月的 SOSP。Xen 的架构里有一个特权域 dom0 负责设备驱动，普通 guest 称 domU 或 DomU。在 Xen 2.0 之前，部分半虚拟化是强制的；Xen 3.0（2005 年 12 月）加入对 Intel VT 的支持，可以跑未改动的 HVM guest。

**硬件辅助。** Intel 在 2005 年推出 VT-x（开发代号 Vanderpool），AMD 在 2006 年推出 AMD-V（开发代号 Pacifica，架构名 SVM），两者互不兼容。VT-x 引入 VMX root 与 VMX non-root 两种执行模式，VMM 跑在 root 模式，guest 跑在 non-root 模式，敏感操作触发 VM exit，guest 状态保存在 VMCS 结构里。硬件辅助把 VMM 写得更简单，也让未改动的 guest 能高效运行。值得注意的是，第一代硬件辅助主要解决"特权指令"问题，速度收益有限，内存虚拟化（MMU 虚拟化）要等后续的 SLAT/EPT/NPT 才补上；VMware 在 2006 年的对比研究中还指出，软件方案在某些负载上仍能跑赢第一代硬件辅助。

半虚拟化并未随硬件辅助出现而消失。Linux 的 virtio 框架把网络、块设备等前端驱动做成半虚拟化接口，配合硬件辅助使用；Hyper-V 面向 Linux guest 提供 VMBus 与集成服务，也属于这一类"guest 知情"的加速通道。全虚拟化、半虚拟化与硬件辅助在今天的 hypervisor 里往往并存，由 VMM 按 workload 选择。

## 六、裸金属与宿主型：VMware 的两条产品线

VMware 是理解"同一个厂商如何划出两层"的最好样本。公司 1998 年成立，头一年处于隐身状态，1999 年 2 月在 DEMO 大会上公开亮相，同年 5 月推出第一款产品 VMware Workstation。这款产品的目标用户是软件开发者与质量保证工程师，用途是在一台桌面 PC 上同时跑多个操作系统做开发与测试，属于典型的宿主型产品。

2001 年 VMware 进入服务器市场，同时推出两款产品：GSX Server 跑在常规操作系统之上，ESX Server 则是直接跑在服务器硬件上、不含底层宿主操作系统的裸金属 hypervisor。ESX 1.0 的发布日按 Wikipedia 记为 2001 年 3 月 23 日。ESX 的核心是 vmkernel 微内核，它有三个接口：硬件、guest 系统、以及服务控制台。2003 年 VMware 推出 VirtualCenter 集中管理、vMotion 在线迁移与虚拟 SMP。VMware 在 2004 年被 EMC 收购，2016 年随 EMC 并入 Dell Technologies，2023 年前后又被 Broadcom 收购，产品线延续至今。2024 年 12 月，VMware Workstation 转为免费软件。

把 Workstation 与 ESX/ESXi 并排看，两条线的差别集中在控制点与启动顺序，而不在"虚拟化"这个词本身。Workstation 是宿主 OS 里的一个进程，宿主 OS 先启动，它再向宿主申请资源；ESXi 自己先启动，再加载 vmkernel 与 guest。这条差别解释了为什么两者在桌面场景都好用，而在数据中心场景里 ESXi 的份额长期更高。

## 七、KVM、QEMU 与 Hyper-V：长进内核与管理栈里的 hypervisor

2000 年代中后期，hypervisor 的形态出现一次收敛：虚拟化能力被塞进已有操作系统内核，而不是另起一个专有内核。

QEMU 由 Fabrice Bellard 开发，2003 年发布首个公开版本，采用的正是动态二进制翻译。它既能做用户态模拟（在一个架构上跑另一个架构的单个 Linux 进程），也能做系统级模拟（跑完整 guest 操作系统），还能与 KVM 配合充当设备模型。QEMU 的定位是模拟器与虚拟化工具的组合体，单独使用时是模拟，配合 KVM 时是虚拟化。

KVM（Kernel-based Virtual Machine）由 Avi Kivity 在以色列创业公司 Qumranet 开发。Kivity 的起点是修补 Qumranet 在 Xen 相关工作中遇到的问题，最初的商业构想是在两台虚拟机之间复制机器状态以实现容错，公司后来转向以 KVM 为 hypervisor 的桌面虚拟化。KVM 于 2006 年 10 月 19 日首次在 Linux 内核邮件列表公布，同年 12 月并入上游内核，随 Linux 2.6.20 于 2007 年 2 月发布。KVM 是一个内核模块，把 Linux 内核本身变成 hypervisor，依赖 Intel VT-x 或 AMD-V，CPU 与内存虚拟化在内核态完成，设备 I/O 交给用户态的 QEMU。这种分工让 KVM 本体相对精简——内核贡献调度、内存管理、电源管理等已有能力，这与 Xen 另立 hypervisor 再配一个 dom0 的思路不同。Red Hat 在 2008 年 9 月宣布收购 Qumranet，KVM 随后成为 RHEL 的默认虚拟化方案。

Hyper-V 的开发代号是 Viridian，发布前一度叫 Windows Server Virtualization。微软在 2007 年 9 月发布社区技术预览（CTP），2007 年 12 月发布首个完整 Beta，Beta 版随 2008 年 2 月的 Windows Server 2008 提供，正式版于 2008 年 6 月 26 日发布并通过 Windows Update 分发；独立的、免费的 Hyper-V Server 2008 于 2008 年 10 月 1 日发布，只保留 Server Core 与 Hyper-V 角色、以命令行方式管理。Hyper-V 的架构已在第四节说明：hypervisor 层负责处理器与内存虚拟化，根分区运行 Windows 承担设备驱动与虚拟化管理，子分区通过 VMBus 把 I/O 请求交给根分区的 VSP，guest 内对应 VSC。从 Windows 8 开始，Hyper-V 也成为个人电脑上的硬件虚拟化组件，取代了 Windows Virtual PC；Windows Virtual PC 本身则源自 2003 年 2 月从 Connectix 收购的 Virtual PC 技术（Connectix 自 1997 年起开发该产品，Windows 版本 4.0 于 2001 年 6 月发布）。

Xen 在企业发行版里的位置可以反映那几年的路线竞争。Novell 的 SUSE Linux Enterprise Server 10 于 2006 年内置 Xen；Red Hat Enterprise Linux 5 于 2007 年 3 月 14 日发布，同样把 Xen 作为主要虚拟化方案，提供 `xen` 与 `kernel-xen` 包，支持半虚拟化与全虚拟化 guest。同一时期 VMware 与 Microsoft 也各自在 2006 年引入半虚拟化的思路。此后 Red Hat 在后续版本逐步转向 KVM，KVM 与 Xen 的此消彼长是 2010 年代虚拟化生态的一条主线。

## 八、薄 hypervisor 与 microVM：把设备模型砍掉

hypervisor 的体积与攻击面在 2010 年代成为独立议题。所谓"薄 hypervisor"（thin hypervisor）或 microvisor，指把 hypervisor 本体压到只保留 CPU 虚拟化、内存虚拟化、中断分发与最基本的隔离，而与设备相关的模拟、管理、驱动全部搬出核心，放进特权域或用户态进程。

Xen 的 dom0 设计已经是这种思路的早期版本：Xen hypervisor 本体不直接驱动物理设备，设备驱动跑在 dom0。这种结构的代价随之显现：AWS 在 Xen 上跑 EC2 时，需要为 dom0 预留 CPU 核心、设备模型与 dom0 竞争资源，dom0 本身又足够大、足够复杂，构成潜在攻击面。AWS 的工程复盘把这三条并列列为"为什么要换架构"的理由。

microVM 是这条路线在云端的落地。AWS 的 Firecracker 于 2018 年 11 月随 re:Invent 开源，用 Rust 写成，基于 KVM 创建 microVM，刻意去掉不必要的设备与 guest 侧功能，只保留网络设备、块设备、可编程间隔计时器、KVM clock、串口与一个用于复位的最小键盘接口。官方给出的量级是每 microVM 内存开销约 5 MB、启动到应用代码约 125 毫秒，配合 jailer 进程做隔离加固。Firecracker 支撑 AWS Lambda 与 Fargate，也被 Kata Containers 等容器运行时集成。

与之配套的是硬件卸载。AWS 在 2017 年 11 月发布 Nitro System（实际开发自 2013 年起），把网络、存储、实例存储与安全等职责搬到专用卡与定制芯片上，主机上只留一个基于 KVM 的 Nitro Hypervisor，官方描述其"管理 CPU 与内存分配，性能与裸金属难以区分"。同一场发布还说明机器的管理通道不再依赖 dom0，Nitro 卡承担管理功能。AWS 的第一代 EC2 服务可追溯到 2006 年 8 月 25 日的公开 Beta，当时使用 Xen hypervisor 与半虚拟化设备，后来在 2017 年 11 月 6 日宣布 C5 实例族改用基于 KVM 的 Nitro 架构。这一段演进把"薄"的两层含义都摆了出来：hypervisor 代码变薄，主机上承担虚拟化职责的软件总量也变薄。

嵌入式领域有另一种薄法。Open Kernel Labs 的 OKL4 Microvisor 把微内核与 hypervisor 合并，用约 10 千行代码构成可信计算基，按作者在 2010 年论文里的说法，microvisor 一词由 microkernel 与 hypervisor 合成。微内核本来就把大多数服务赶出内核态，再叠加虚拟化接口，得到的隔离原语比传统 hypervisor 更小，适合手机基带、车载等场景。这条支线提醒读者：hypervisor 的顺序高低并不由代码行数决定，规模小是设计选择，不是优越性的证据。

## 九、容器：共享内核的操作系统级隔离

容器这一支与虚拟机并行发展了三十多年，二者的分野在"共享内核"四个字。

最早的一块砖是 `chroot`。该调用在 Version 7 Unix（1979 年）中出现，其作用是改变进程可见的根目录，使程序无法命名目录树之外的路径。Wikipedia 引述 Marshall Kirk McKusick 的说法，称 Bill Joy 在 1982 年 3 月 18 日前后为构建 4.2BSD 测试环境而加入该调用，这处具体年份在来源之间不一致（维基百科正文记 1979 年）「待核实」。chroot 当初并不是安全工具，这一点在后来的安全文献中被反复指出。

2000 年，FreeBSD 4.0 引入 jail 机制。Poul-Henning Kamp 与 Robert N. M. Watson 的论文《Jails: Confining the omnipotent root》把 jail 描述为在保留 UNIX root 模型简洁性的同时，把超级用户的权力限制在一个划定区域内，每个 jail 有自己的文件系统子树、进程集合与 IP 地址。jail 的实现建立在 `chroot` 之上，但补上了对进程可见性与超级用户权限的限制。

2004 年 2 月，Sun 的 Solaris 10 测试版（build 51）公开了 Solaris Containers 与其中的 Zones，Solaris 10 正式版于 2005 年发布。Zones 把资源控制与边界隔离结合起来，能在同一内核上跑多个近似独立的系统环境。Linux 一侧，命名空间的实现自 2002 年起逐步进入内核（Al Viro 的 mount namespace 出现在 Linux 2.4.19），cgroup 的前身"process containers"由 Google 的 Paul Menage 与 Rohit Seth 在 2006 年提出，2007 年更名为 Control Groups，最终并入 Linux 2.6.24（2008 年）。2008 年出现的第一版 LXC（LinuX Containers）把这些内核能力包装成完整的容器管理接口，官方文档把 LXC 描述为"介于 chroot 与完整虚拟机之间的东西"，并明确其目标是在不需要独立内核的前提下提供尽可能接近标准 Linux 安装的环境。

Docker 把这条线推到大众面前。Solomon Hykes 于 2013 年 3 月 15 日在 PyCon 上首次公开演示 Docker，同年 3 月开源；最初以 LXC 作为默认执行环境，2014 年 3 月的 0.9 版改用自研的 libcontainer（用 Go 写成）。同年 9 月 19 日，dotCloud 与 Red Hat 宣布在 OpenShift 上合作；10 月 29 日，dotCloud 公司更名为 Docker Inc.。Docker 的核心价值在打包与分发：镜像把应用与依赖固化下来，容器启动的语义接近进程。编排层的代表 Kubernetes 由 Google 工程师在 2014 年发起，首次提交于 2014 年 6 月 6 日，2014 年 6 月 10 日由 Eric Brewer 在 DockerCon 上对外宣布，1.0 版于 2015 年 7 月 21 日发布，同年捐赠给新成立的 CNCF，成为该基金会第一个托管项目。Google 内部更早的 Borg 系统从 2003 至 2004 年起就在用 Linux 容器。

判据在于隔离面。容器里的进程直接向宿主内核发起系统调用，命名空间改变的是它能"看到"哪些资源，cgroup 改变的是它能"用"多少资源，二者都不提供独立的 CPU 特权模式与独立内核。虚拟机里的 guest 有自己的内核，敏感指令被 VM exit 拦截，硬件层提供隔离。这两个边界不能互相替换：内核漏洞在容器场景下可能影响宿主机上所有共用同一内核的容器，在多租户环境下这一点促使云厂商把容器塞回轻量虚拟机里跑——Firecracker microVM 与 Kata Containers 就是这类组合，Firecracker 官方 README 明确列出已集成进 Kata Containers 等容器运行时。

## 十、WSL2 为什么算虚拟机

Windows Subsystem for Linux 的两次架构正好对应本文的两层。WSL1 于 2016 年在 Microsoft Build 大会公布，随 Windows 10 周年更新（2016 年 8 月 2 日）正式提供。它的做法是在 Windows NT 内核上实现一层 Linux 系统调用翻译，把 Linux 二进制发出的系统调用转换为 NT 内核能处理的操作。这层翻译覆盖不全，一些应用无法运行；WSL1 因此被误当成"虚拟机"，但按本文的坐标，它没有独立内核、没有虚拟硬件、也没有 hypervisor 介入，落在模拟与翻译层。

WSL2 于 2019 年 5 月 6 日公布，2020 年随 Windows 10 版本 2004 正式版提供（具体 GA 日期「待核实」）。微软在发布博客里写明：WSL2 使用虚拟化技术，把一个真实的 Linux 内核跑在一个轻量工具虚拟机（lightweight utility virtual machine）里。这个虚拟机基于 Hyper-V 架构，作为"虚拟机平台"（Virtual Machine Platform）可选组件提供，在支持 WSL 的所有 SKU 上可用，包括 Windows 10 家庭版。Linux 发行版按 Microsoft Learn 的描述"作为隔离的容器运行在被托管的 VM 内部"。内核由微软从 kernel.org 的稳定分支构建并针对 WSL2 调优，随 Windows 更新维护。

WSL2 与 Hyper-V 的关系在早期还带来一个实际冲突：启用 WSL2 后，依赖 Hyper-V 的第三方虚拟化工具（当时的 VMware 与 VirtualBox 6 之前版本）无法运行。VirtualBox 在 2018 年 12 月发布的 6.0 版加入以 Hyper-V 为后备执行核的能力，微软则提供 Hypervisor Platform API，让第三方虚拟化软件借用 Hyper-V 架构；WSL2 也可以借助嵌套虚拟化在虚拟机里运行。

WSL2 在体验上"不像虚拟机"，来自托管与集成两方面的减负：发行版与虚拟机由系统管理，用户不做 VM 配置，启动进入 shell 常在两秒内，Windows 与 Linux 之间可互调进程、共享剪贴板与文件系统。这些属于产品化包装，不改变底层事实——WSL2 里有真实 Linux 内核，跑在 Hyper-V 的虚拟化层之上。与 WSL1 相比的另一处证据是文件系统：微软官方对比表写明 WSL2 在解压 tar 包时比 WSL1 快最多 20 倍，跨操作系统文件访问反而变慢，这正是"独立内核加 9P 式跨 VM 文件共享"这种结构的典型特征。

## 十一、中文语境里的分层：网吧、还原软件与安卓模拟器

虚拟化在中文互联网的普及路径与欧美数据中心叙事并不重合。对普通用户而言，最常接触的三类形态分别是网吧机房管理、系统还原软件与安卓模拟器。

网吧无盘系统是本世纪初从国外无盘技术改良后引入国内网吧的方案。按公开资料，无盘工作站在本地没有硬盘，通过服务器提供的镜像完成启动与数据读写，属于客户端/服务器架构的集中管理模式。网管维护一份母盘镜像，所有终端从同一份镜像启动，软件更新与故障恢复因此从"逐台处理"变成"改一次母盘"。这类实践的关注点在批量部署与恢复，与 hypervisor 的路线无关，却同样是"把终端与硬件解耦"的工程思路。

与之配套的是还原类软件。冰点还原（Deep Freeze）与影子系统（PowerShadow）是中文用户最熟悉的两款。影子系统的机制是创建一个虚拟系统，让写入操作进入临时的影子层，重启后回到真实系统；冰点还原则把系统盘冻结到某个还原点，重启恢复。这两类工具的做法更接近快照与写时复制，与虚拟化在隔离目标上相通，在实现层级上不同。

对游戏玩家而言，接触面最广的形态是安卓模拟器。BlueStacks 由 Rosen Sharma、Jay Vaishnav、Suman Saraf 于 2009 年 4 月 25 日创办，2011 年 5 月首次在 Citrix Synergy 大会上展示，2011 年 10 月发布 Alpha 版；其底层采用虚拟化技术，公司在多次采访中把这一层描述为对用户不可见。中国厂商随后推出同类产品：夜神的开发团队成立于 2015 年 3 月，运营主体为北京多点在线科技有限公司（2015 年 2 月 5 日注册），其模拟器支持多开与挂机；网易 MuMu、逍遥（MEmu）、雷电（LDPlayer）等产品也在同一市场出现。这些产品的技术栈通常包含一个为 x86 定制的 Android 内核与图形渲染层，目标是把手机游戏搬到键盘鼠标与大屏幕上，并支持多开账号。把它们叫作"模拟器"在中文里已成习惯，英文语境里同款产品也常自称 emulator，但从架构上看，其中不少是"定制 Android 系统加虚拟化 / 容器化层"的组合。

桌面端的另一类实践是老系统兼容。为运行只能在旧版 Windows 上启动的游戏或为跨区玩日文游戏，用户常在 VMware Workstation 或 VirtualBox 里装一台 Windows XP/7 虚拟机，或干脆装双系统。这一步用到的正是第六节描述的宿主型产品，与网吧的还原卡、手机上的安卓模拟器共同构成了中文玩家侧的虚拟化记忆。

## 十二、常见误解与"倒灌"

**误解一：容器是轻量虚拟机。** 容器不虚拟化硬件，guest（容器内进程）与宿主共享内核、共享系统调用入口。轻量与否不是关键，关键是隔离面不同：虚拟机边界在虚拟硬件与 VM exit，容器边界在命名空间、cgroup 与内核安全模块。把两者互换会带来安全上的错误预期。

**误解二：Type 1 一定比 Type 2 快。** 分类描述的是控制点位置，不描述具体实现的性能。KVM 与 bhyve 是内核模块，归类存在争议；Hyper-V 是微软认定的 Type-1，但设备路径仍要经过根分区；第一代硬件辅助在某些负载上不如精心优化的软件方案。性能取决于 I/O 路径、驱动质量与 workload，与类型标签只有间接关系。

**误解三：WSL1 是虚拟机。** WSL1 没有独立内核，也没有 hypervisor 介入，做法是系统调用翻译。WSL2 才引入真实 Linux 内核与轻量 VM。两者可以在同一台机器上并存，发行版可随时升降级。

**误解四：模拟与虚拟化是同一件事。** QEMU 不加载 KVM 时是跨架构模拟，加载 KVM 后是同架构虚拟化。模拟依赖动态二进制翻译，虚拟化要求非特权指令在真实 CPU 上直接执行，两者的性能量级与适用范围都不同。

**误解五：半虚拟化已经过时。** 半虚拟化的核心是"guest 知情并主动配合"。virtio 设备驱动、Hyper-V 的集成组件与 VMBus、Xen 的 hypercall 都是这套思路的产品化延续，配合硬件辅助一起使用。

**误解六：裸金属实例等于无虚拟化。** 云厂商提供的"裸金属"实例通常仍由固件、管理控制器与分区机制围起来，只是不再向客户暴露 hypervisor 层。把"裸金属"理解为"机器上没有任何虚拟化组件"并不准确。

**误解七：把需要隔离的现代需求算到 1960 年代的账上。** 这一条属于叙事上的倒灌，值得单独展开。CP/CMS 当年解决的问题是：一台昂贵主机如何同时伺候多个课题组，以及如何让为旧机器写的程序继续运行。它的用户在同一机构内部，信任关系是前提而非要克服的障碍。云多租户是 2006 年 EC2 之后才规模化的问题；容器编排与声明式交付是 2013 年 Docker 与 2014 年 Kubernetes 才出现的问题；把"零信任"这一套安全理念放进 1960 年代的虚拟机语境，等于给当年的人派了七十年后的作业。同理，把 WSL2 说成"微软终于做了虚拟机"、把 Firecracker 说成"容器的替代品"，都属于用后来概念改写早期动机。

**误解八：虚拟化必然带来显著性能损失。** 现代硬件辅助配合半虚拟化驱动后，CPU 与内存路径的开销已降到较低水平；开销更可能出现在 I/O、嵌套虚拟化、内存超分与跨架构模拟这几处。把"虚拟化等于慢"当作通则，会忽略具体机制。

| Nitro System | 定制芯片 + KVM 衍生 hypervisor | 机器级 | 硬件辅助 | AWS C5 及之后实例 | 把设备与管理职责卸载出主机 |
| FreeBSD jail | 宿主内核 | 操作系统级 | 操作系统级隔离 | FreeBSD 4.0（2000） | 在保留 root 模型下隔离服务 |
| Solaris Zones | 宿主内核 | 操作系统级 | 操作系统级隔离 | Solaris 10（2004 测试版 / 2005 正式版） | 商用 UNIX 上的工作负载整合 |
| LXC | 宿主内核 | 操作系统级 | 操作系统级隔离 | LXC（2008） | 把 namespace + cgroup 包装成容器 |
| Docker | 宿主内核 | 操作系统级 | 操作系统级隔离 | Docker（2013） | 应用打包与交付一致性 |
| WSL1 | Windows NT 内核上的翻译层 | 宿主内核（系统调用翻译） | 系统调用翻译 | Windows 10 周年更新（2016） | 在 Windows 上跑 Linux 工具链 |
| WSL2 | Hyper-V 架构上的轻量工具 VM | 机器级 | 硬件辅助 | Windows 10 2004 及之后 | 提高文件性能与系统调用兼容性 |
